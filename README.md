# SoL-Pi

A working prototype of **SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent
Harness** (Liu et al., arXiv:2609.20519, NVIDIA / NTU / MIT, 2026).

The paper's claim is that token efficiency for long-horizon agents can be won at the
**harness** layer — the code that mediates between a model and its environment — without any
model training. This repo implements that idea end to end: a runnable agent harness, the four
mechanisms the paper's search retained, and the Auto-Research Loop that discovers and gates
them.

## Running it as an agent

The harness is also an **ACP v1** agent speaking stdio JSON-RPC, so a host (Codync, or anything
else that speaks the protocol) can drive the same loop the research measures. `npm run agent`
is the entry point; the server is `src/agent/`.

- **`initialize` → `session/new` → `session/prompt`**, with `session/update` notifications as the
  turn runs and `session/request_permission` before anything that touches the filesystem or runs a
  command. `session/cancel` aborts a turn in flight.
- **Two tool backends, chosen from the client's advertised capabilities.** A client that offers
  `fs.readTextFile` + `fs.writeTextFile` and `terminal` gets every read, write, and run delegated
  to it; anything less and the agent falls back to running them locally in the session's `cwd`.
- **A provider seam, Anthropic first.** `SOLPI_PROVIDER=anthropic` (default) with
  `ANTHROPIC_API_KEY`, or `SOLPI_PROVIDER=scripted` with `SOLPI_SCRIPT=<path>` for a fully offline
  run driven by a recorded script — the same script format the research suite uses.
- **stdout is the protocol.** The console is redirected to stderr before the stream is built, so a
  stray log lands in the host's logs instead of corrupting a line a host would reject.
- **A bad configuration answers the request instead of dying.** The provider resolves on the first
  `session/new`, so a missing key returns an error the host can show its user.

`probes/live-agent.mjs` sends one real prompt through the server, and `probes/host.ts` drives the
server from the other side of a stdio pipe as a full ACP host — advertising fs and terminal, so
the client-delegated backend runs over a real connection. CI runs the host probe offline on every
push, and both probes live when a key is configured, because they are the only tests that exercise
the model seam against the real API.

## The base harness

`Harness` (`src/core/harness.ts`) is the "Pi"-style loop: expose a tool schema, let the model
emit calls, execute them against the environment, append observations to the context, repeat.
Every mechanism is a `Mechanism` that hooks into one of seven points without altering control
flow:

| Hook | When it runs | Used by |
| --- | --- | --- |
| `transformTools` | before the schema is sent | Action Fusion (adds `then_run`), ObservationPack (adds `recall_observation`) |
| `transformCalls` | after the model emits, before execution | Action Fusion (merges calls) |
| `transformResult` | after a tool runs | Evidence-Preserving Reducer |
| `projectObservation` | before an observation enters the context | ObservationPack (archiving) |
| `transformContext` | before every request | ObservationPack (substitution), Online Context Compact |
| `resolveTool` | when a mechanism-contributed tool is called | ObservationPack (serves `recall_observation`) |
| `onPlanStepComplete` | at plan boundaries, once per newly-done step | Online Context Compact |

Mechanisms with per-run state implement `reset()`, called at the top of every `run()` so a
reused harness does not accumulate archives across runs.

The model backend is a `ScriptedModel` whose policy is fixed per task. Because the model's
behaviour is held constant across harness configurations, any measured token difference is
attributable to the harness — which is the property the paper's evaluation depends on.

## The four mechanisms

**Action Fusion** — an edit followed by a separate build/test command costs three API calls.
Fusion adds an optional `then_run` to file-mutation tools and returns both outcomes in one
observation: 3 calls → 2. Commands that inspect the mutation result (`cat`, `grep`, …) are
left separate, matching the paper's fallback boundary.

**Online Context Compact** — at each plan-step completion the harness estimates remaining
requests (from observed requests-per-step and unfinished steps), caps that estimate by what
would fill the context window, and then applies the **cost gate**: compact only when projected
input savings exceed the cache-rewrite cost. Later compactions require a larger margin to
account for unrecovered rewrite cost. Compaction is also permitted near the window limit,
provided it actually shortens the context.

**ObservationPack** — results above 10 KiB are archived locally, sent in full for the next two
requests, then replaced by a stable handle plus a head/tail excerpt of complete lines. The
original is recoverable: the mechanism contributes a `recall_observation` tool that serves the
exact text (or a 4 KiB page of it) by handle, so the substituted view's instruction to recall is
an affordance the agent can actually act on. The mechanism runs on `transformContext`, so
substitution applies to *recurring* observations in later requests, not just the first one.

**Evidence-Preserving Reducer** — build/test logs from the tool allowlist (`test`, `pytest`,
`npm`, `build`, `cargo`) that are 4 KiB or larger are compressed by a low-cost extractor model
into a receipt, which a deterministic verifier then checks: schema, source hash, exit status,
verbatim quotes, non-empty evidence, and size. Any failure falls back to the exact original. It
runs before ObservationPack, which recognizes the receipt marker and skips it so verified
evidence is preserved.

## The Auto-Research Loop

`AutoResearchLoop` (`src/research/loop.ts`) implements the search half of the paper's Fig. 2:

1. Evaluate the baseline harness on the search environments.
2. For each candidate: propose, implement, review, run.
3. **Capability gate** — every capability metric must stay within its predeclared tolerance.
   Metrics and tolerances are fixed before search and are not under the optimizer's control.
4. **Efficiency gate** — at least one declared efficiency metric must improve.
5. Among candidates passing both gates, retain the **nondominated** set.
6. **Freeze**, then evaluate on the held-out benchmark. Held-out results never feed back into
   search; `heldOutVerdict` applies the same two gates to them and a failure rejects the
   candidate. The frozen configuration is whatever the search actually retained (`summary.best`),
   never a hardcoded id.

The default acceptance rule fixes `aggregateScore` within 5% and requires `tokenTraffic` or
`cost` to improve by at least 5%.

## Environments

Following the paper's two construction paths (`src/tasks/corpus.ts`):

- **Repository-derived** — a pre-fix repo state paired with a hidden regression test that
  fails before the accepted patch and passes after it.
- **Verifier-driven** — an executable verifier defines success, allowing multiple solution
  paths.

The corpus is a compact stand-in for the paper's 535 environments, plus a deliberately
long-horizon task whose verbose build logs give the context-heavy mechanisms something to act
on. Held-out environments are kept in a separate export and are never touched by search.

Four things worth flagging in these numbers:

- **Action Fusion measures ~0% here, and that is honest.** The corpus's scripted policy already
  emits the write and the run in a single turn, so there is no intermediate round trip for fusion
  to eliminate. An earlier run reported −23.6% for this candidate, but that was an artifact: the
  model emitted `then_run` as a bare string, the validator dropped it, the test never ran, and the
  large log never entered the context. The saving was missing work, not saved work.
- **The reducer dominates** once it matches the logs the environment actually emits. It carries the
  frozen candidate on both the search and the held-out tasks, which is the paper's central
  claim — efficiency won at the harness layer without touching the model.

- **The context-substituting mechanisms look smaller than they did.** These figures bill the
  prefix cache: each request pays the read price for the part that repeats the previous request
  verbatim, the write price for the appended tail, and the full input price for anything a
  mechanism rewrote mid-context. ObservationPack substitutes archived observations *in place*, so
  every substitution invalidates the suffix that was already cached — its saving falls from 79.5%
  to 50.7% once that rewrite is billed, and OnlineContextCompact's falls from 33.7% to 11.4%. The
  reducer escapes the effect because it acts before the observation reaches the context at all.
  An earlier build recorded zero cache traffic in the ledger, which made substitution look free;
  `probes/measure-cache-prefix.ts` measures the effect directly.
- **The reducer's headline saving moved 96.7% → 90.2%, deliberately.** The corpus gained
  `verifier-003`, a task whose build log is 55,248 bytes of rustc warnings — a format the
  extractor's rules do not cover, so the reducer provably compresses nothing on it and saves
  exactly 0 cost (published under `activation.reducerUnrecognisedFormat` in
  `research-results.json`). The published number now includes the task that exposes the gap
  instead of quietly excluding it. The held-out verdict is unchanged: 95.5% saved, PASS.

## Honest differences from the paper

- The model is a deterministic scripted backend, not GPT-5.6 Sol or Opus 5. Its policy is
  fixed so that token deltas reflect harness changes only.
- The corpus is 7 search + 2 held-out environments, not 535 + EdgeBench's 51.
- Token estimation is character/word based, not a real BPE tokenizer.
- Cost figures use a fixed price table and are not comparable in magnitude to the paper's
  production runs. They do bill the prefix cache — read price for the part that repeats the
  previous request, write price for the appended tail, full input price for anything rewritten
  mid-context — so a mechanism that rewrites the context is charged for the invalidation, not
  just the shorter result. What is comparable is the *shape*: score preserved, cost down, and
  savings concentrated in the large-object mechanisms.
- The extractor model is a rule-based stand-in for GPT-5.6 Luna. Evidence is defined as a typed
  predicate over the log formats the environment actually emits (pytest banners, `E …` assertion
  lines, bracketed `[summary]`/`[warn]` lines), ordered by evidentiary value. The fidelity knob
  drops quotes by a hash-seeded rule rather than a PRNG, so a given log always yields the same
  receipt. **Its coverage is measured, not assumed** — `probes/measure-extractor-coverage.ts`
  runs the rules against real failure logs: rustc, go, tsc, maven, and eslint all match **zero**
  rules and yield no quotes, while a real pytest failure log yields evidence. One corpus task,
  `verifier-003`, is built to expose the gap: its build is a 55,248-byte rustc warnings log, the
  reducer reduces nothing, records **3 unrecognised-format fallbacks**, and saves **exactly 0**
  cost against the same task without the mechanism — published under
  `activation.reducerUnrecognisedFormat` in `research-results.json`. An empty receipt counts as
  an unrecognised format, not a verification failure, so the stats cannot dress a coverage gap
  up as a failed verification.
- The paper's evaluation runs the candidate stack against real provider APIs. The research path
  here stays in-process — no network call is ever made by `npm run research`, so the numbers above
  are reproducible offline. The agent path is separate and can reach a real provider, but nothing
  it observes feeds the published figures.
